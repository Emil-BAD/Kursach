# Архитектура платформы управления общежитием

## Обзор

Данный проект представляет собой backend-платформу для управления студентческим общежитием и связанными с ним процессами: проживание, санитарный контроль, коммуникации, дисциплина, финансовые операции и административные задачи. С точки зрения архитектуры это не одноразовый CRUD-модуль, а расширяемый продуктовый сервис, рассчитанный на работу в реальной среде управления жилым комплексом.

Цель архитектуры — обеспечить:

- разделение ответственности между слоями
- безопасный контроль доступа пользователей
- масштабируемую модель доменных сущностей
- единый подход к работе с данными и API
- возможность дальнейшего сопровождения и развития продукта

## Принципы проектирования

### 1. Разделение доменной логики и HTTP-слоя

Система отделяет:

- API-обработчики (роутеры)
- бизнес-логику (services)
- работу с хранилищем данных (repositories)
- модели данных (SQLAlchemy models)
- схемы валидации (Pydantic schemas)
- общие платформенные компоненты (core)

Это позволяет поддерживать код в чистом состоянии и не смешивать бизнес-процессы с транспортным уровнем FastAPI.

### 2. Контроль доступа на уровне ролей и прав

В проекте используется RBAC-модель, где доступ к операциям определяется ролями пользователя и правами, которыми он обладает. Это критично для общежития, где разные типы пользователей имеют разные полномочия:

- студент — доступ только к своему профилю и своей комнате
- комендант — управление своим общежитием
- администратор — полный доступ к платформе
- члены советов и санитарных комиссий — специальные административные сценарии

### 3. Единый контракт API

Все доменные модули строятся вокруг предсказуемых HTTP-ответов, общей структуры данных и централизованной обработки ошибок.

### 4. Готовность к продуктовой эволюции

Архитектура позволяет развивать проект в сторону:

- frontend-панелей
- мобильного приложения
- администрирования по нескольким корпусов
- аналитики и отчетности
- интеграций с внешними системами

## Основные доменные модули

### 1. Users and identity

Модуль пользователей отвечает за:

- профили студентов и персонала
- привязку к общежитию, блоку и комнате
- роли и права
- просмотр информации по себе и по другим пользователям при наличии доступа

### 2. Dormitory domain

Сущности общежития и комнат обеспечивают:

- структуру объектов недвижимости
- привязку жильцов к конкретной комнате
- хранение инвентаря и географии размещения
- параметры общежития и дополнительные данные

### 3. Cleanliness and discipline

Модуль контроля чистоты и нарушений позволяет:

- назначать проверки по комнатам
- выставлять оценки
- вести историю проверок
- отслеживать нарушения и дисциплинарные меры

### 4. News and events

Коммуникационный слой поддерживает публикацию:

- новостей и объявлений
- событий и важной информации
- календаря мероприятий для общежития

### 5. Payments and billing

Финансовый блок покрывает:

- баланс пользователя
- счета и задолженности
- историю платежей
- пополнения и подтверждение операций
- управляемые статусы оплаты

### 6. Service requests

Модуль заявок позволяет студентам и персоналу создавать и отслеживать обращения: ремонт, обслуживание, запросы и т.д.

## Слой API

### v1

Версия v1 содержит стандартизированные маршруты для базовых бизнес-сценариев:

- авторизация
- профиль пользователя
- новости
- события
- админские операции
- санитарные проверки

### v2

v2 разработан для более зрелого и системного взаимодействия с финансовыми сервисами:

- dashboard по платежам
- баланс и история оплат
- текущие счета
- пополнения пользователем
- создание и обновление счетов администраторами

## Слой бизнес-логики

Services отвечают за сценарии использования:

- проверка прав доступа
- проверка корректности данных
- агрегация данных из нескольких сущностей
- определение статусов и допустимых операций
- формирование ответа клиенту

Например:

- `PaymentV2Service` управляет платежной логикой
- `Cleanliness` сервис работает с проверками комнат и оценками
- `UserService` обрабатывает пользователя как бизнес-объект
- `NewsService` управляет новостным контентом

## Слой данных

`repositories/` является абстракцией над SQLAlchemy и отвечает за запросы к базе данных. Это позволяет:

- централизовать обращение к модели
- избегать дублирования SQL-логики
- скрыть детали БД от сервисного слоя
- проще поддерживать сложные запросы с joinedload, фильтрацией и пагинацией

## Безопасность и авторизация

Безопасность реализована на нескольких уровнях:

- JWT-аутентификация
- проверка токена через зависимость FastAPI
- ограничение доступа через RBAC
- централизованная обработка ошибок и состояний авторизации
- CORS-конфигурация и настройка окружения через .env

## Обработка ошибок

Проект использует централизованную архитектуру исключений вместо разрозненных HTTPException по коду. Это дает:

- единый контракт ошибок
- предсказуемый HTTP-статус
- меньше дублирования
- лучшую устранимость и поддержку

## Пагинация и унифицированные ответы

Система строит типовые ответы для списков и отчетов, чтобы фронтенд и мобильные клиенты работали через одинаковые контракты.

Это особенно важно для:

- пользователей
- платежей
- новостей
- событий
- историй проверок

## Масштабирование

Архитектура подготовлена для дальнейшего роста:

- по числу пользователей

- erp-ориентированной административной панели

## Ключевые решения

### Почему FastAPI

FastAPI выбран как основа платформы, потому что:

- быстро создает production-ready API
- хорошо работает с Pydantic-схемами
- подходит для сервисной архитектуры
- облегчает документирование и интеграцию с frontend

### Почему SQLAlchemy

SQLAlchemy обеспечивает:

- выразительный ORM-уровень
- гибкую работу с запросами
- поддержание сложного домена общежития
- безопасное разделение данных по сущностям

### Почему RBAC

Ролевая модель критична для этой предметной области, поскольку доступ к информации и операциям существенно отличается между студентами, комендантами и администраторами.

## Результат

Архитектура проекта отражает типичный продуктовый подход к разработке backend-системы для управления жилым пространством: модульность, безопасность, контроль доступа, прозрачность данных и расширяемость.

Это позволяет не просто хранить данные, а строить вокруг них полноценный цифровой сервис для управления общежитием.
